# ADR-0003: ручные связки уровня 2 и уровня 3

Статус: реализовано как явный строгий режим. Старый /v1 остаётся для frozen compatibility; production-задачи со строгой связкой требуют --binding-policy и --worker-id, mTLS обязателен.

Оператор локально утверждает паспорт: binding_id, level2_id, algorithm_version, model_version, package_sha256, input_contract, level3_manifest_id, data_version, manifest_sha256, allowed_workers. Политика связывает SHA256 клиентских сертификатов с допустимыми binding_id. Manifest утверждает HTTPS origins, source_id, part_id, размер и checksum частей, хеш каждой записи. Ядро хранит эти метаданные, позицию чтения и состояние алгоритма; полные исходные наборы не сохраняет.

Выбор выполняет control через /v1/bindings/select. Discovery выбирает только точный passport_sha256; подстановка другого сектора отсутствует. Data получает только разрешённый каталог и отправляет /v1/bindings/tasks. Проверяются точная версия, источник, часть, индекс и hash записи. Legacy attach/tasks/snapshot/restore в строгом режиме заблокированы. После завершения manifest оператор явно вызывает /v1/bindings/close, затем выбирает следующую связку.

Уровень 3 получает одну ограниченную NDJSON-часть за раз, проверяет всю часть перед отправкой, затем отправляет записи последовательно. Части остаются на вручную подготовленных серверах. Это последовательная сборка потока, а не автоматическое шардирование, secret sharing или запуск произвольного окружения. Один сборщик на связку. При потерянном ответе задача автоматически не повторяется: следующий запуск читает подтверждённый cursor. Повтор уже принятого индекса отклоняется. После потери RAM процессов гарантии восстановления отсутствуют.

Snapshot state_version=2 переносит точный паспорт и cursor через существующий staged transfer с checksum/resume/rollback. Приёмник должен заранее иметь утверждённую локальную политику, пакет и модель той же версии. До source release несовместимость позволяет откат; после release действует существующий протокол завершения активации. Старые v1 snapshots state_version=1 остаются только в legacy режиме; bound snapshot несовместим со старым сервером. Существующие wire-схемы /v1 не изменены; binding endpoints и схемы добавлены. Новые клиенты не предполагают поддержку binding старым сервером.

Граница доверия: локальная политика, конфигурация TLS, код алгоритма и системный администратор доверенные. Manifest hash проверяется относительно локально утверждённого паспорта; отдельной цифровой подписи нет. Package digest должен вычисляться по реальному коду, весам и ресурсам доверенным загрузчиком. Демо включает два исходных файла, без обученных моделей. Алгоритм выполняется внутри процесса без sandbox; это не защита от злонамеренного утверждённого кода или администратора. На серверах частей задавайте отдельные client_pins для нужного сектора: нельзя давать чужому сектору доступ к его файлам. Шифрование обеспечивается mTLS при передаче; шифрования дисков, PKI revocation и горячей ротации здесь нет.

Изменение данных/модели требует нового паспорта и версии, ручного утверждения и развёртывания. Автообучения, скачивания исполняемого кода и обмена между алгоритмами нет. Лимиты прототипа: часть/сообщение/snapshot до 64 KiB, до 4096 записей на manifest, один активный алгоритм. Для больших наборов нужен отдельный дизайн компактных commitments и checkpoint storage.

Проверки: unit tests паспортов; реальный mTLS e2e с четырьмя внешними источниками, двумя секторами, переносом cursor между workers; отказ чужому сертификату, altered part/record, несовместимому пакету; frozen legacy client/server в обе стороны в CI всех трёх репозиториев.
